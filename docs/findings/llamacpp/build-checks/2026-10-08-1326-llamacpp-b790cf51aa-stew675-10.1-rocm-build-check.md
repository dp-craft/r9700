## Methodology & caveats

- Same session, same model file, same flags; per backend the previous build runs first, then the new one. llama-swap is stopped for the whole run (restarted after) and `stack/gpu/gpu_exclusive.sh` (asserts ≥ 26000 MiB free) runs before every arm.
- Each arm is one `bench/perf/model-bench/run.sh` → `llama-bench` invocation: the `pp P` tests, then the `-pg P,G` tests, r=1 each. llama-bench's per-test warmup is off (it re-runs every prompt in full); one throwaway pp1000 and pg1000,32 run first instead — warming the prefill and decode paths — and are dropped.
- r=1: no noise estimate. The 5% bar sits above the largest sd seen at r=3 (ROCm prefill 4.5%); still, a single ▼ deserves a re-run with `--reps 3` before acting on it. The smallest prompts take well under 1 s, so their prefill cells are the noisiest.
- Raw llama-bench throughput: no MTP / speculative decoding, no server, no prompt cache. llama-swap's served decode (MTP on) is higher — compare builds here, not against serving wall-clock.
- One model (dense 27B, Q4_K_XL) and one KV type: MoE or other quants can move differently.
- Cross-report comparisons are only valid when the GPU/Host line (kernel, HIP, Mesa) is identical.
