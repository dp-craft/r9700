# Technical Research: hipfire alongside llama-swap

Date: 2026-09-10
Topic: install, configure and wire `warpfront/hipfire` in next to the existing llama-swap setup
Constraints from the requester: llama-swap must be able to switch between engines, `generate.py` must be
aligned too; first model needed is Qwen 3.8 27B MQ4-Pro with MTP (falling back to MQ4 + DFlash draft if
MTP is unavailable); priority is **maximum performance on the R9700**.

## Strategic Summary

hipfire is a genuinely good fit for this box — it is an RDNA-native HIP/ROCm engine in Rust whose
**gfx1201 (RDNA4 / R9700) is a first-class, fully-validated target**, not an afterthought. llama-swap
front-ends *any* OpenAI-compatible server, so swapping between hipfire and the existing llama.cpp
builds is a supported configuration rather than a hack. The real cost is not the wiring — it is the
**prerequisites**: this machine currently has neither a ROCm HIP development stack nor a Rust
toolchain, and hipfire needs both because it builds from source and JIT-compiles kernels.

**The load-bearing finding:** the existing ROCm llama.cpp row in llama-swap works only because the
binary ships its own `libamdhip64.so.7` next to it (`LD_LIBRARY_PATH=.../llamacpp-b10375:.../llamacpp`)
and spoofs the GPU with `HSA_OVERRIDE_GFX_VERSION=12.0.1`. That is a *runtime* shim. hipfire cannot
reuse it: it compiles kernels at install/run time and therefore needs the real SDK — `hipcc`, HIP
headers, `libhsa-runtime64.so`. Installing ROCm properly is step 1 and it is a system-level change.

Worth noting as a point in hipfire's favour: its stated design goal is running natively across RDNA
generations *"without lying about the hardware identity"* — i.e. no `HSA_OVERRIDE_GFX_VERSION` needed
for gfx1201, unlike the current ROCm llama.cpp row.

## What hipfire Is

> **Fast, AMD-native LLM inference — RDNA-first, CDNA-supported.**
> Rust + HIP + Redline. No Python in the hot path. Ollama-style UX.
> — [README](https://github.com/warpfront/hipfire)

- Stable release **v0.2.1**; **v0.3.0** in beta (headlined by MQ4R + Redline across RDNA, Qwen 3.8 27B,
  Muse Glimmer 30B).
- License Apache-2.0 (v0.3.0+); earlier releases dual MIT/Apache-2.0.
- OpenAI-compatible HTTP daemon, default bind `0.0.0.0:11435`, **no auth and no TLS**.
- Own quantization formats (`.mq4`, `.mq4p`, `.mq4r`, `.mq5`, `.mq2`, `.mq2lloyd`, `.mfp4`, …), with a
  GGUF **import/quantize** path (`hipfire quantize ./model.Q4_K_M.gguf --install --register my:tag`).
- Weights live in `~/.hipfire/models/`; config in `~/.hipfire/config.toml`.

### Published gfx1201 numbers — and what they do *not* cover

The headline R9700 row, for **Qwen 3.6 35B-A3B MQ4R**:

| GPU | Arch | TG128 AR | 8-turn avg decode | ctx | final turn | validation |
|---|---|---|---|---|---|---|
| Radeon AI PRO R9700 | gfx1201 | **203.9 tok/s** | **169.5 tok/s** | 22.2K | **146.7 tok/s** | 8/8 clean; both recall probes 3/3 |

`REDLINE.md` gives the mechanism: *"Sealed fixture: HIP median 174.670 tok/s, PM4 median 202.460 tok/s
(1.159×)"* — the retained-PM4 path is worth ~16% over ordinary HIP dispatch on this exact GPU. The
campaign report claims the full arc as ~110 → 203.9 tok/s.

**Caveat that matters for your decision:** those are **Qwen 3.6 35B-A3B MoE** numbers — a different
family and size from the Qwen 3.8 27B **dense** model you want, and MoE with 3B active params decodes
very differently from a 27B dense forward pass. There are **no published gfx1201 numbers for Qwen 3.8
27B**. So the strong figures above justify running the benchmark; they do not predict its result.
This is the single biggest reason to bench before rewiring.

## Requirements

- ROCm **6.4+** for RDNA4 (gfx1200/gfx1201); project baseline is ROCm 6+. ROCm 7.2.x is the current
  stable line for Ubuntu 24.04 and adds explicit RDNA4 coverage.
- The selected ROCm root **must** provide `lib/libamdhip64.so`, `libhsa-runtime64.so`,
  `include/hip/hip_runtime.h`, `bin/hipcc`. Runtime-only installs are explicitly insufficient.
- Rust/cargo on `PATH` — the installer refuses without it and does *not* bootstrap Rust.
- Disk: tens of GB under `~/.hipfire/models/` for 27B-class models (the 27B MQ4 artifact alone is
  ~15–16 GB). With 55 GB free this is workable but not roomy.

## The model you asked for: `qwen3.8:27b-mq4-pro`, and why MTP is off the table

**MQ4-Pro exists.** From `docs/MODELS.md`:

```
| `qwen3.8:27b-mq4-pro` | `qwen3.8-27b.mq4-pro` | 16.46 | 18 | q8 | MQ4V2 Pro |
```

16.46 GB on disk, 18 GB minimum VRAM, q8 KV by default. On a 32 GB R9700 that leaves real headroom.
Note the tag spelling: the 3.8 dense ladder uses the hyphenated `-mq4-pro` / `.mq4-pro`; the bare
`.mq4p` extension belongs to the 3.6 A3B line (`qwen3.6:35b-a3b-mq4p`). The full 3.8 27B ladder is
`-mq4-xt` (speed) → `qwen3.8:27b` (`.mq4`, default) → `-mq4-pro` → `-mq5`.

**MTP is not available for this model.** MTP in hipfire is carried by an `mtp.file` sidecar, and
`MODELS.md` states:

> Several A3B entries carry an `mtp.file` sidecar name (`qwen3.6-35b-a3b.mtp`). MTP enablement is
> config/runtime gated (`mtp_mode`, env); registry presence alone is not admission.

The Qwen 3.8 **dense** registry rows carry **no** `mtp.file` sidecar — MTP is documented for the A3B
MoE models only. The config keys exist globally (`mtp_mode` default `"auto"`, `mtp_k` default `3`;
env `HIPFIRE_MTP_MODE` / `HIPFIRE_MTP_K`, with an extra `HIPFIRE_QWEN_MTP=1` gate on the Qwen path),
but with no MTP weights for 3.8 27B there is nothing for them to enable.

**So your stated fallback is the live branch: pull the DFlash draft.** The recommended controller is:

```
| `qwen3.8:27b-draft-mq4` | `qwen38-27b-dflash-mq4.hfq` | 1.21 | 16 | `qwen3.8:27b*` (recommended controller) |
```

1.21 GB, and the `qwen3.8:27b*` glob means it drafts for the whole 3.8 27B family including
`-mq4-pro`. Alternatives exist (`-draft-mq3`, `-draft-mq5`, `-draft-mq6`) but mq4 is the documented
recommendation.

DFlash is **opt-in** (`dflash_mode` defaults to `"off"`) and is **mutually exclusive with MTP** — the
speculator builder picks exactly one mechanism in the cascade DFlash → MTP → n-gram. Since MTP is
unavailable here, DFlash is simply the mechanism, with no conflict to manage.

This is also the one place where the current llama.cpp setup and hipfire line up conceptually: the
existing `models.yaml` already treats `mtp:` and `draft:` as mutually exclusive (both write
`--spec-type`, and `generate.py` raises if a row sets both). Same rule, different engine.

## Approach 1: hipfire as a third llama-swap backend (recommended)

**How it works.** llama-swap is documented as working with *"any server that provides the `/v1/`
generative api endpoints"* — it is not llama.cpp-specific. A hipfire row becomes a normal model entry
whose `cmd` launches `hipfire serve 127.0.0.1 ${PORT}` in the foreground; llama-swap health-checks it,
routes to it, and SIGTERMs it when another model is requested. `:9292` stays the single front door, so
`runner.config.json`, `opencode` and `smart-gateway` need **zero** changes — a hipfire row is just a new
`modelId` at `http://127.0.0.1:9292/v1`.

**The three llama-swap fields that make this work:**

| Field | Why it matters here |
|---|---|
| `checkEndpoint` | **Works as-is.** hipfire exposes `GET /health` returning `{ status, model, loading_model, pid, native }`, so llama-swap's `/health` default is correct — no override needed. |
| `useModelName` | *Essential.* llama-swap routes by its own id, but hipfire expects a registry tag (`qwen3.8:27b-mq4-pro`) in the `model` field — and a mismatched tag **triggers a model reload**, not an error. `useModelName` rewrites it on the way upstream. |
| `cmdStop` | Optional but clean: `hipfire stop` SIGTERMs the tracked pid after ownership checks (`${PID}` macro available). It deliberately does *not* kill stale reused pids — it removes the pidfile instead. |

**Daemon lifecycle facts that make this safe** (from `docs/SERVE.md`):

- `hipfire serve` runs in the **foreground** (Ctrl-C stops it); `-d` is what detaches. llama-swap needs
  foreground, so **omit `-d`** — this is the single most important detail in the whole integration.
- Shutdown is a clean SIGTERM against the pid tracked in `~/.hipfire/serve.pid`.
- One model resident per daemon; only one generation holds the daemon lock at a time (bounded queue).
- `healthCheckTimeout` is already 600 in the generated config — comfortably above hipfire's own 60 s
  detached-readiness poll and any first-run kernel warmup.

**One overlap worth knowing:** hipfire will reload on a per-request `model` mismatch by itself, so it
has a mini model-swapper built in. Do not lean on it — with `useModelName` pinning each llama-swap row
to exactly one tag, llama-swap stays the only component making swap decisions. Two swappers racing
over one GPU is a failure mode, not a feature.

**Pros**
- One front door; nothing downstream is touched, so the change is additive and reversible.
- A/B against llama.cpp is a one-line model switch in `/dp-test-llm` or `runner.config.json`.
- Idle TTL, groups and the existing opencode menu sync all keep working.

**Cons**
- Model swaps mean full daemon restarts (process start + weight load + possible kernel JIT).
- hipfire is **not flag-compatible with llama-server** — see the generator problem below.

**Complexity:** M

## Approach 2: standalone daemon on :11435, side by side

Run `hipfire serve 127.0.0.1 11435` permanently and add separate `baseUrl` entries in
`runner.config.json`. No llama-swap involvement.

**Pros:** fastest to a first measurement; zero risk to the generated llama-swap config; daemon stays
warm so no reload cost between benchmark runs.
**Cons:** second front door; VRAM contention with whatever llama-swap has loaded; opencode menu does
not see it; two lifecycles to manage by hand.
**Best when:** the goal is a clean benchmark, not daily driving.
**Complexity:** S

## Approach 3: bench standalone first, then fold into llama-swap

Phase 1 = Approach 2 purely for measurement; Phase 2 = Approach 1, gated on Phase 1 winning.

**Pros:** the generator surgery is only paid for if the numbers justify it, and Phase 1 gives the
baseline the decision needs. **Cons:** two integration passes.
**Complexity:** S then M

## The generator problem (this is the real work)

`~/.config/llama-swap/generate.py` (747 lines) is not a thin templater — it is llama.cpp-shaped:

- `VULKAN_BIN` / `ROCM_BIN` point at two `llama-server` builds; `main()` emits exactly two macros and
  picks `binref = "${vulkan}" if be == "vulkan" else "${rocm}"`.
- `cmd_for()` builds a **llama-server argv**: `--model <gguf>`, `-c`, `-ngl 99`, `-fa on`, `-ub/-b`,
  `--jinja`, `--temp/--top-p/--top-k/--min-p`, `--chat-template-file`, `--spec-type draft-mtp`.
- `models.yaml` rows are keyed on `path:` (a **relative GGUF path** under `/home/dev/models/gguf`),
  plus `ctx`, `kv`, `mtp`, `draft`, `family`, `backends`, `templates`, `np`, `kv_unified`.
- `full_id()` bakes ctx/kv/mtp/backend/template/effort into the llama-swap id, and `sync_opencode()`
  pushes those ids into the opencode provider menu.

**Almost none of that transfers.** hipfire takes no GGUF path, no `-c`, no `-ngl`, no sampler flags and
no `--chat-template-file`. Its knobs live in `~/.hipfire/config.toml` and in a *persistent per-model
overlay* (`hipfire config <tag> set generation.temperature 0.7`) — i.e. **global state, not argv**.

That is the one architectural friction worth naming plainly: the current design expresses every
variant (template × purpose × sampler × effort) as a **different argv on the same binary**, which is
exactly what lets llama-swap treat them as separate rows. hipfire expresses them as **mutations of a
config file**, so two hipfire rows differing only in temperature would launch byte-identical commands
and silently share whatever the config file last said. The generator's `full_id()` docstring already
warns about precisely this failure mode for pinned template kwargs ("whichever survives silently
misreports what it runs").

**So the aligned-generator design must be:**

1. Add `HIPFIRE_BIN` and a third macro: `"hipfire": "{HIPFIRE_BIN} serve 127.0.0.1 ${PORT}"`.
2. Add `hipfire` to the `backends:` vocabulary and give `full_id()` a `hf` tag (like the existing
   `rocm` tag) so hipfire rows can never collide with llama.cpp rows.
3. Add a `hipfire_tag:` field to `models.yaml` rows — the registry tag (`qwen3.8:27b`) that replaces
   `path:` for this backend. Emit it as `useModelName`.
4. Branch in `main()`: `be == "hipfire"` uses a new `hipfire_cmd_for()` and **must not** call
   `cmd_for()`. Emit `checkEndpoint: /v1/models` (or `none`) on those rows and skip the
   `GGML_VK_ALLOW_GRAPHICS_QUEUE` / `HSA_OVERRIDE_GFX_VERSION` / `LD_LIBRARY_PATH` env blocks — they
   are llama.cpp-specific and the override in particular is the thing hipfire exists to avoid.
5. **Raise** if a hipfire row sets llama.cpp-only keys (`templates`, `kv_unified`, `np`, `draft`,
   `spec_p_min`, `ctk`) — same defensive posture the file already takes for `mtp` + `draft` together.
   Silently ignoring them is how the "misreports what it runs" bug gets in.
6. One row per hipfire tag, one purpose, no sampler expansion — until per-request sampling is
   confirmed to be honoured over the OpenAI API rather than the config overlay.

## Recommendation

**Approach 3, in three gated phases: bench standalone → opencode by hand → llama-swap.**

1. **Phase 1 — standalone bench.** `hipfire serve` on `:11435`, `/dp-test-llm` against it and against
   the current Vulkan 27B row. Gate: does it actually win on this box, on a dense 27B?
2. **Phase 2 — opencode provider.** Add a hand-maintained `hipfire` provider next to the existing
   `llama-swap` and `ollama-local` ones and drive it manually. `sync_opencode()` only rewrites
   `.provider["llama-swap"].models`, so this survives `generate.py` untouched — `ollama-local` already
   proves the pattern. This phase is where reasoning-effort and real context depth get settled.
3. **Phase 3 — llama-swap backend.** Only once manual use is satisfying, pay for the generator work.

Each phase is independently reversible and each answers a question the next one depends on. The
generator surgery — the only expensive, hard-to-reverse piece — is deferred until two cheaper phases
have justified it.

The requester's stated priority is maximum performance on the R9700, and the honest position is that
nobody here has measured hipfire on this box yet. The vendor's gfx1201 numbers are strong enough to
justify the ROCm install, but not strong enough to justify rewriting a 747-line generator before a
single token has been produced locally. Phase 1 costs a ROCm install plus one `hipfire serve` and
answers the only question that matters. Phase 2 is then a well-understood, additive generator change
against a known-good baseline.

The prerequisite work (ROCm SDK + Rust) is unavoidable in every approach, is the bulk of the elapsed
time, and is a system-level change to a machine that currently runs a working Vulkan stack — so it is
worth doing deliberately rather than as a side effect of "trying something out".

## Concrete steps

### Step 0 — ROCm HIP SDK (the long pole; system-level)

RDNA4 needs ROCm ≥ 6.4; the current stable line for noble is 7.2.x. The amdgpu kernel driver already
works here (Vulkan runs, `/dev/kfd` present), so **skip DKMS**:

```bash
wget https://repo.radeon.com/amdgpu-install/7.2.4/ubuntu/noble/amdgpu-install_7.2.4.70204-1_all.deb
sudo apt install ./amdgpu-install_7.2.4.70204-1_all.deb
sudo amdgpu-install --usecase=rocm --no-dkms
sudo apt install rocm-hip-sdk          # this is the part that brings hipcc + HIP headers
sudo usermod -aG render,video "$USER"  # re-login afterwards
```

Verify before going further — all four must exist:

```bash
/opt/rocm/bin/hipcc --version
/opt/rocm/bin/rocminfo | grep -m1 gfx        # expect gfx1201
ls /opt/rocm/lib/libamdhip64.so /opt/rocm/lib/libhsa-runtime64.so
ls /opt/rocm/include/hip/hip_runtime.h
```

Two caveats. First, `/opt/rocm` currently holds a stray `core-7.13/` skeleton — check what package
owns it before installing over the top. Second, ROCm issue #6110 reports gfx1201 being rejected by the
HIP runtime with *"has 2 ISAs but can only support a single ISA"*; if that bites, it is a known issue
with a known shape rather than a mystery.

Kernel 7.0 is newer than ROCm's tested 6.8/6.17 pair — `--no-dkms` avoids the module build, but this
is the most likely place for friction.

### Step 1 — Rust toolchain

```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source "$HOME/.cargo/env"
```

### Step 2 — hipfire

The installer is a source-build bootstrap: it clones to `$HIPFIRE_HOME/src` (default `~/.hipfire/src`),
runs `cargo build --release -p hipfire-cli`, then hands off to `hipfire setup --source <repo>`. It
requires cargo and will not install Rust for you.

```bash
PIN=v0.2.1
curl -fsSL "https://raw.githubusercontent.com/warpfront/hipfire/${PIN}/scripts/install.sh" \
  -o /tmp/hipfire-install.sh
sha256sum /tmp/hipfire-install.sh          # eyeball it — it is a piped installer
bash /tmp/hipfire-install.sh --ref "$PIN" --rocm-root /opt/rocm --gpu-arch gfx1201 --strict-rocm
```

`--strict-rocm` is deliberate: it fails loudly rather than silently falling back if the SDK is
incomplete. Given the vendored-library mess already on this box, a loud failure is the outcome you
want. If v0.2.1 predates the Qwen 3.8 27B ladder, use `--branch beta` instead — the 3.8 27B and MQ4R
work is headlined for v0.3.0.

Then the gate that decides everything:

```bash
hipfire diag        # GPU arch, VRAM, HIP/ROCm, kernel locations, model dir
```

If `diag` does not report gfx1201 cleanly, stop — nothing downstream is worth doing.

### Step 3 — pull the model and its draft

```bash
hipfire pull qwen3.8:27b-mq4-pro     # 16.46 GB
hipfire pull qwen3.8:27b-draft-mq4   # 1.21 GB, drafts for qwen3.8:27b*
hipfire list                          # confirm local availability
hipfire list -r                       # authoritative live registry, if a tag is missing
```

~18 GB against 55 GB free. Fine, but keep an eye on it — `/` is already at 85%.

### Step 4 — configure (loopback + DFlash)

```bash
hipfire config set host 127.0.0.1        # default is 0.0.0.0 with NO auth and NO TLS
hipfire config set speculation.dflash on # or "auto"; default is off
hipfire config list                       # verify overlay + provenance
```

Binding to loopback is not optional hygiene here — the default really is all-interfaces, unauthenticated.

### Step 5 — Phase 1: benchmark standalone (gate)

```bash
hipfire serve qwen3.8:27b-mq4-pro     # foreground; :11435
curl -s http://127.0.0.1:11435/health
curl -s http://127.0.0.1:11435/v1/models
```

Add a temporary profile in `runner.config.json` pointing at `http://127.0.0.1:11435/v1` with
`modelId: qwen3.8:27b-mq4-pro`, then run `/dp-test-llm` against it and against the existing
`bench-27b-frog-q4km` row. Same task, same repetitions. That comparison is the whole decision.

Measure DFlash both ways (`speculation.dflash on` vs `off`) — speculative decoding is workload-shaped,
and the current setup already learned that lesson the hard way with `--spec-draft-p-min` ("tune on
tok/s, NOT on acceptance rate").

**Gate:** if it does not beat the current Vulkan 27B row on tok/s at comparable quality, stop here.
Delete the temporary profile and nothing else has changed.

### Step 6 — Phase 2: wire into opencode for manual driving (only if Phase 1 wins)

This is safe, and there is already a working precedent for it in your own config.

`sync_opencode()` in `generate.py` reads the whole `~/.config/opencode/opencode.json`, mutates
**only** `.provider["llama-swap"].models`, and writes the file back. It does not touch any other
provider. Your `ollama-local` provider (`:11434`, hand-maintained, 11 models) has been surviving
regenerations on exactly that basis — so a third, hand-maintained `hipfire` provider is preserved
across `python3 generate.py` by construction, not by luck.

Add alongside the existing two:

```json
"hipfire": {
  "npm": "@ai-sdk/openai-compatible",
  "name": "hipfire (R9700 native)",
  "options": { "baseURL": "http://127.0.0.1:11435/v1", "apiKey": "dummy-key" },
  "models": {
    "qwen3.8:27b-mq4-pro": {
      "name": "qwen3.8:27b-mq4-pro",
      "limit": { "context": 65536, "output": 32768 }
    }
  }
}
```

Keep the daemon up (`hipfire serve qwen3.8:27b-mq4-pro -d` is fine here — llama-swap is not involved
yet, so detaching is an advantage), pick it from `/models` in opencode, and drive it by hand.

Two things to settle during this manual phase, because they decide what Phase 3 can express:

1. **Context limit.** `65536` above is a placeholder, not a measured value. `MODELS.md` notes 50K Q8
   is "tight but feasible" on 24 GB and 200K Q8 needs >32 GB or CASK compression; with 32 GB and a
   16.46 GB model you are somewhere in between. Confirm the real usable depth before trusting it.
2. **Reasoning effort.** The llama-swap rows expose effort through opencode `variants`
   (`chat_template_kwargs.reasoning_effort` + `reasoning_budget_tokens`) — a llama.cpp `--jinja`
   template mechanism. hipfire owns reasoning through its own three-axis mode/effort/cap contract in
   its config and OpenAI layer, and Qwen 3.8 is effort-native (`low`/`medium`/`xhigh`). Whether the
   same request-body fields reach it, or whether effort must move into `hipfire config`, is the open
   question this phase exists to answer. Deliberately no `variants` block above until you know.

### Step 7 — Phase 3: fold into llama-swap (only after manual testing satisfies)

Target `models.yaml` row shape:

```yaml
  - id: qwen38-27b
    hipfire_tag: qwen3.8:27b-mq4-pro
    family: QWEN38
    backends: [hipfire]
```

Target generated block:

```yaml
  "qwen38-27b-mq4pro-hf":
    name: "qwen38-27b-mq4pro-hf  [hipfire, dflash]"
    cmd: |
      ${hipfire}
    useModelName: qwen3.8:27b-mq4-pro
    cmdStop: hipfire stop
```

with `macros: "hipfire": "<HIPFIRE_BIN> serve 127.0.0.1 ${PORT}"`. Then `python3 generate.py`,
`./start_llama_swap.sh restart`, and the model appears at `:9292` like any other — `runner.config.json`
just references the new id.

At this point the standalone daemon and the Phase 2 `hipfire` opencode provider become redundant:
stop the detached daemon (`hipfire stop`) so it cannot race llama-swap for the GPU, and either drop
the hand-written provider or keep it pointed at `:11435` purely as a debugging bypass — but never run
both at once.

### Rollback

Each phase rolls back independently, which is the point of the ordering:

| Phase | Undo |
|---|---|
| 1 — standalone bench | delete the temporary `runner.config.json` profile; nothing else touched |
| 2 — opencode provider | delete the `hipfire` provider block; `generate.py` never knew about it |
| 3 — llama-swap | remove the `models.yaml` row, `python3 generate.py`, restart |

hipfire itself uninstalls by removing `~/.hipfire` — the installer ships no uninstall path. ROCm is
the only step that genuinely changes the machine, and it is the one to think twice about.

<chosen_approach>
- name: Phase 1 standalone benchmark -> Phase 2 opencode provider (manual) -> Phase 3 llama-swap backend
- prerequisites: ROCm 7.2.x HIP SDK (>=6.4 required for gfx1201), Rust toolchain
- install: source build via scripts/install.sh (needs cargo; delegates to `hipfire setup`)
- model: qwen3.8:27b-mq4-pro (16.46 GB, 18 GB VRAM) + qwen3.8:27b-draft-mq4 (1.21 GB) for DFlash;
  MTP is A3B-only and does not apply to the 3.8 27B dense line
</chosen_approach>
<architecture>
- pattern: llama-swap remains the single OpenAI front door on :9292; hipfire becomes a third
  backend macro alongside ${vulkan} and ${rocm}
- components: ROCm SDK, hipfire CLI+daemon, generate.py hipfire branch, models.yaml hipfire_tag field
- data_flow: runner/opencode -> :9292 llama-swap -> (swap) -> hipfire serve 127.0.0.1 ${PORT} -> GPU
</architecture>
<files>
- phase 1: runner.config.json (TEMPORARY bench profile at :11435, deleted after)
- phase 2: ~/.config/opencode/opencode.json (NEW hand-maintained "hipfire" provider; safe from
  generate.py, which only rewrites .provider["llama-swap"].models — see ollama-local precedent)
- phase 3: ~/.config/llama-swap/generate.py (HIPFIRE_BIN, macro, backend branch, hipfire_cmd_for)
  + ~/.config/llama-swap/models.yaml (hipfire_tag field, backends: [hipfire])
- unchanged throughout: tools/smart-gateway/*, tools/agentic-code-runner/* (that is the point)
- reference: generate.py full_id()/cmd_for()/main() for the existing two-backend branch pattern;
  opencode.json .provider["ollama-local"] as the second-provider template
</files>
<implementation>
- start_with: ROCm SDK install and `hipfire diag` — do not touch the generator until diag is clean
- order: ROCm -> rust -> hipfire install -> pull model+draft -> GATE: standalone benchmark ->
  opencode provider + manual testing -> GATE: satisfied? -> generator branch
- gotchas: `hipfire serve` must run WITHOUT -d (llama-swap needs foreground); hipfire is NOT
  llama-server flag-compatible; sampling lives in persistent config overlays not argv; default bind is
  0.0.0.0 with no auth/TLS (set host 127.0.0.1); /health exists so llama-swap's default checkEndpoint
  is correct; useModelName required to translate llama-swap id -> hipfire registry tag, and a
  mismatched tag silently RELOADS rather than erroring; do not reuse the HSA_OVERRIDE_GFX_VERSION /
  LD_LIBRARY_PATH shims from the rocm rows; MTP is unavailable for 3.8 27B dense - use DFlash draft
- testing: `hipfire diag`, then curl /health and /v1/models, then /dp-test-llm against the new modelId
  with DFlash both on and off
</implementation>
