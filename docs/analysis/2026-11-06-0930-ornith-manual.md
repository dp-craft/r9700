# Ornith 1.5 35B-A3B: when and how to use it

- **Date:** 2026-11-06 · **Kind:** manual, from measured runs
- **Model:** `keptn/ornith-1.5-35b-a3b-w4a8` (MoE, about 3B active; 4-bit experts, FP8 activations)
- **Engine:** `stilldeadcode/radiance:1.16.0` on the R9700 (gfx1201, 32 GB). Starter: `ornith_rad_mtp.sh start|stop|status`
- **Client:** Claude Code headless, through the `ornith` skill (`skills/ornith/scripts/ornith.sh`)
- **Compared with:** Claude Haiku 5.5; see [the Haiku manual](2026-11-06-0930-haiku-manual.md)
- **Evidence:** [use cases](2026-11-05-0814-ornith-use-cases.md), [document extraction vs Haiku](2026-11-04-2207-sly-radiance-ornith-vs-haiku-high-effort.md), [serving speed](2026-11-04-1746-ornith15-radiance-vs-sly-35b-27b.md), run data in `bench/runs/2026-11-05-0320-ornith-usecases/`

All numbers are `MEASURED` unless marked. Most come from one run per setting (n=1), on synthetic or repo fixtures.
Treat a score difference under 0.05 as a tie.

## In short

| | |
|---|---|
| **Use Ornith for** | Clear tasks whose result a script or test can check: JSON and log questions, code inventories, tests, renames, clear bug fixes, fixed-form summaries, document restructuring through a manifest |
| **Don't use it for** | Exhaustive lists, file paths, full configurations, complete incident lists, retyping text, final verdicts |
| **Why use it** | No API tokens, and about 4× faster than Haiku on the median task (1.1–12.7× across 15 tasks) |
| **Main risk** | Output that looks finished but is wrong: right numbers under wrong labels, tests that fail on the original code, missed caveats |

## Strengths

| What | Result |
|---|---|
| Computing over JSON with `jq`/`python3` | 1.0 at 8k, 41k and 131k tokens; 14–19 s |
| Code inventory | 1.0, 1.0, .995 at 8k, 36k, 88k |
| Facts copied from a document | Exact line 20/20, 30/30, 32/35; 0 invented at every size; accuracy held at 185k context |
| Planted faults and explicitly labelled incidents | All planted log faults at 18k, 151k and 340k; every planted document incident |
| Tests for given code | 1.0, 16 of 16 mutants killed, 41 s |
| Rename, mechanical edit, clear bug fix | 1.0; 45 s and 14 s |
| Summary numbers | 1.0 at 6k–55k. Conclusions 2–3 of 3, the same range as Haiku |
| Restructuring documents without retyping | 0 lost lines in 6 of 6 runs at 6k–55k, when a script moves the text from Ornith's manifest |
| Labels on bug text | Kind .795 vs Haiku .718 at 9k |

## Weaknesses

| What | Ornith | Haiku | Note |
|---|---|---|---|
| Complete error-class list, 340k log | 16, 16, 21 of 21 | 21 of 21 | Fine for finding faults, not for the full list |
| File paths from text | .57–.76 | .94–.97 | Get paths with `grep` |
| Full configuration in notes | 4 of 8 | 8 of 8 | |
| Incidents listed in notes | 13 (6 deep notes) | 24 | |
| Incidents in footnotes, hedged text or list ends | 0 of 3 | 4–6 of 6 | Same brief and fixture. 12 prompt and brief variants didn't close it (best: 2 of 3 on one item) |
| Conclusions (4 deep reports) and cross-document conflicts | 8–9 of 12; 0 valid conflicts | 11–12 of 12; 1/1 and 4/4 valid | Several reports per session lower Ornith's conclusions: 7 of 12 vs 10 of 12 with one report per session |
| Retyping text | 6k took 480 s and 69k generated tokens; 2 more runs didn't finish in 10–12 min | 242 s, no loss | Never ask Ornith to rewrite a document |
| Code from a spec | 34, 26, 29 of 34 hidden tests; one parser looped forever | 34 of 34 | A draft; your tests decide |
| Bug classification at 33k | .58 | .71 | Severity is weak (.56 exact) |

**Critical errors in notes** happen at about 2 per 6 deep notes: a sign or direction reversed, certainty strengthened ("rules out" where the source says "strong"), one setting's number applied to another.

## Speed and capacity

| | Value |
|---|---|
| Decode, one request | 219.8 / 205.0 / 174.5 tokens/s at 10k / 50k / 100k context |
| Prefill, cold prompt | 13,059 / 8,029 / 5,301 tokens/s at 10k / 50k / 100k |
| Time to first token | 0.78 / 6.15 / 18.5 s at 10k / 50k / 100k |
| Generation in agent sessions | 89–241 tokens/s |
| 3 sessions in parallel | 254 tokens/s total vs 174 alone (1.46×), about 100 per session; a 4th waits in the queue |
| Server start | About 45 s |
| Context | 262,144 tokens per request. Claude Code compacts near 187–196k |
| VRAM | Peak 28.6–31.8 GiB of 32 GiB across agent runs (up to 32,511 MiB on a speed probe); GTT 94–339 MiB, no spill |
| Speculative decoding | MTP, 3 draft tokens, 50.0% accepted |

- **Most of the output is reasoning:** 41–97% of generated tokens, 82–88% on document work. A slow session is usually long reasoning, not slow decoding.
- **Reasoning costs context:** each document's reasoning stays in the session, 7.4–9.2k tokens per document. Plan about 100k of source per session; one large document fits up to about 166k (`INFERRED`).

## Thinking, effort and sampler

- **Thinking is always on.** The starter sets `enable_thinking: true`.
  - A request with `enable_thinking: false` turns it off: 26 tokens instead of 591 on a probe.
  - Quality without thinking is untested, so don't turn it off.
- **The effort setting does nothing.** `low`, `medium`, `high`, `xhigh` and an invalid value gave identical token counts at temperature 0.
  - The chat template reads only `enable_thinking` (`CLAIMED`, model card), and the starter maps `none` and `minimal` to `high`.
  - So "think harder" has to come from the task itself, not from a setting.
- **Sampler: keep the default** (temp 1.0, top_p 0.95, top_k 20, presence penalty 1.5).
  - The precise preset (temp 0.6, presence 0) showed no benefit in 7 comparisons.
  - Examples: bug text .653 vs .705, code from a spec .706 vs 1.0. It didn't fix retyping either.

## System prompt

Claude Code's own prompt is about 3,350 chars. The operator's `dp` prompt adds 285 tokens. Results against Claude Code's prompt alone:

| Profile | `dp` appended | Use |
|---|---|---|
| `data` (`jq`, `python3`) | 33% fewer generated tokens, score +.02 (9 tasks) | `dp` appended (the skill's default) |
| `code` (edit, tests, git) | 15% fewer tokens, a tie (4 tasks) | `dp` appended (default) |
| `read` (documents, logs) | 20% more tokens, score −.05 (12 tasks); conclusions 6–7 of 12 vs 8–9, more critical errors | Claude Code's prompt alone (default) |

- **Don't replace Claude Code's prompt on `code`.** With `dp` as the whole prompt, code from a spec scored 1.0, .824 and .382 (mean .735), against .941 appended, and used 36% more tokens. On notes, replacing and appending tied.
- **Extra rules don't buy recall.** Prompts that ask for skeptical re-reading, a map of the source, a self-check, "meaning over keywords" or a "borderline bucket" didn't make Ornith list incidents it misses. It reads the whole file and judges those passages irrelevant.

## How to use it efficiently

1. **Route by checkability.** If a script, test or `grep` can confirm the result, Ornith is the cheap choice. If the value is in completeness or judgement, use Haiku, or Ornith plus a review.
2. **Make it compute, not reason.** JSON questions dropped from 48–89 s to 17 s at the same score once it used `jq`/`python3`.
3. **Never let it retype text.** Have it write a manifest (line ranges and targets) and let a script move the bytes.
4. **One document per session for notes.** Give fixed output fields and a real example line: a placeholder like `CLASS|` gets replaced in every run.
5. **Keep briefs short when a tool does the work.** Added rules and self-checks rarely raised scores; only bug classification clearly gained.
6. **Run up to 3 sessions in parallel** for batches. It's 1.46× the throughput, but each session is slower, so don't do it for one urgent task.
7. **Check what decides something:** numbers by spot-check, paths with `grep`, code by running your own tests (with a timeout), lists against a count.

## Limits and failure signs

| Sign | Meaning | Action |
|---|---|---|
| `ORNITH ERROR: error_max_turns` | It looped at the 80-turn cap | Rework the brief; don't just raise the cap |
| Many permission denials on `code` (7–15 per session) | It tries `node`, `npx --no-install`, compound commands or paths outside the repo | Run the tests yourself |
| "All tests pass" | One session shipped 41 tests that fail on the original code | Run them |
| A run past 10 min on a small input | Long reasoning or retyping | Stop it, discard the output, change the brief |
| A format line rewritten | Placeholders or schema not followed | Validate the format by script |
| Desktop apps crash | Likely VRAM nearly full (113–232 MiB free) next to a browser (`INFERRED`, n=1) | Stop the server when the card is needed elsewhere; nothing else GPU-heavy runs beside it |

## Risks

- **`python3` on the `data` profile can run anything.** Use it only on material you trust.
- **Interrupted sessions** can leave output that looks complete. Discard anything from a cut or timed-out run.
- **Results are fixture-based and mostly n=1.** Real repositories, with tool paths outside the work dir, can behave differently (`INFERRED`).
