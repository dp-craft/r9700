# Benchmark: vLLM 0.29.0 attention backends on Qwen3.8-27B-INT4 — R9700 (gfx1201)

- **Date:** 2026-09-11 20:47 · **Track:** engine-bench (llama-benchy against a live vLLM server) + torch-profiler kernel traces
- **GPU/Host:** AMD Radeon AI PRO R9700, gfx1201, 32624 MiB · kernel 7.0.0-31-generic · ROCm 10.0.0 · HIP 7.15.26333 · Ryzen 5 3600, 31 GB RAM
- **Runtimes:** vllm 0.29.0+rocm723 · torch 2.12.0+git6bbd260 (built vs ROCm 7.2.3) · triton 3.7.1 · transformers 5.17.0 · compressed-tensors 0.17.0 · host venv `bench/dl/vllm-venv` (no Docker) · `VLLM_ROCM_USE_AITER=0`
- **Model:** RedHatAI/Qwen3.8-27B-INT4 @ `bf08f3db` (compressed-tensors W4A16, group 128, symmetric; bf16 lm_head; hybrid 16 full-attn + 48 Gated-DeltaNet layers, head_dim 256, vocab 248320)
- **Data:** `bench/runs/2026-09-11-2047-vllm-qwen38-27b-int4/` (`mtp0/`, `mtp0-tritonattn/`, per-arm `server.log`, `gpu_samples.csv`, `profile/`)
- **Baseline (indicative only):** `docs/analysis/2026-09-11-1716-llamacpp-b10909-build-check.md` — different tool (llama-bench), different quant (UD-Q4_K_XL GGUF), q8_0 KV

## Summary

vLLM 0.29.0 runs this checkpoint correctly on RDNA4, but **out of the box it is unusable at depth**: the default ROCm attention backend cannot use its custom paged-attention kernel for this model (head_dim 256, hybrid KV block 1568) and falls back to a Triton kernel launched with a grid of `(num_seqs, num_kv_heads)` = **(1, 4)** — 4 workgroups on 64 CUs — giving **2.8 tok/s decode at 32k** (MEASURED, engine gauge). Selecting `--attention-backend TRITON_ATTN`, whose decode path splits each sequence into 16 parallel softmax segments, raises that to **14.12 tok/s** and also improves the shallow shape (**16.17 vs 14.67 tok/s decode, 1085 vs 723 tok/s prefill**). The trade is 32k prefill: **222.4 vs ~470 tok/s**, because TRITON_ATTN's wide-tile tuning for head_dim 256 is gated to NVIDIA Blackwell, leaving 2 query rows per program on ROCm (VERIFIED in source). Even so TRITON_ATTN wins the whole 32k request (**~292 s vs ~13 min**). Against llama.cpp b10909 (indicative) vLLM still loses every shape — 2.7× on the 32k request — and profiling shows why: decode spends only ~26 ms of its ~59 ms step on bandwidth-bound weight reads; the rest is **963 kernels/step with a ~19.5 µs floor each plus 23 ms of idle gaps**, an overhead that appears only in the CUDA-graph-replayed decode steps. The INT4 kernel itself is not the problem (~574 GB/s, ~90% of spec bandwidth).

## Consequences & root causes (ultrathink)

1. **The default backend is a depth trap.** `use_rocm_custom_paged_attention` requires `head_size == 128` and `block_size == 16`; this model has head_dim 256 and vLLM inflates the KV block to 1568 so the attention page ≥ the mamba page. Both gates fail, so ROCM_ATTN falls back to `kernel_paged_attention_2d`, launched at grid `(num_seqs, num_kv_heads)` = (1, 4) for single-stream decode (VERIFIED, `vllm/v1/attention/ops/chunked_prefill_paged_decode.py:461`). 4 workgroups on 64 CUs, each walking 32k of KV serially → **2.8 tok/s**, with the memory controller at **7–8% busy** and power at 115 W of 300 W (MEASURED via `amd-smi metric -u`). **Therefore: never run a head_dim-256 hybrid on vLLM/ROCm defaults; always pass `--attention-backend TRITON_ATTN`.**
2. **"GPU busy 100%" is meaningless on this stack.** During the collapse the sysfs/`amd-smi` GFX activity read 100% while UMC read 7–8%. The bandwidth figure derived from tokens/s (≈42 GB/s ≈ 6.5% of spec) matches UMC almost exactly (MEASURED, cross-validated). **Therefore: use memory-controller activity and power as the saturation proxies in this repo, not `gpu_busy_pct`.**
3. **The INT4 quantized path is healthy; vLLM's problem is dispatch, not math.** INT4 GEMV at ~574 GB/s and lm_head at ~638 GB/s are at hardware limits (INFERRED byte counts from config dims). The weight-read floor is ~25.8 ms/token ≈ 38 tok/s, yet the step takes 59 ms. The difference is ~963 kernels × (~19.5 µs execution floor + ~23.8 µs gap). **Therefore: the lever is kernel count and dispatch cost, not a better GEMM.**
4. **The ~19.5 µs floor is specific to CUDA-graph-replayed decode steps (MEASURED, strong).** Identical kernels measured 1.2–2.5 µs in the piecewise prefill step and 19.4–19.6 µs in every full-graph decode step (e.g. `triton_poi_fused_mul_silu_slice_3`: 3 fast of 3037 calls, all in step 0; `triton_poi_fused_5`: 38 fast, all in step 0). Kernels as short as 1.04 µs exist in both traces, so this is **not** a constant profiler offset. Whether the ~18 µs is real graph-node dispatch cost or rocprofiler attributing inter-node overhead into each node is **OPEN** — but either way only ~26 ms of the 59 ms step is real work. **Therefore: the decisive next test is `--compilation-config '{"cudagraph_mode":"PIECEWISE"}'`; the ceiling if all overhead vanished is ~27.7 tok/s (INFERRED from the 36.03 ms measured kernel time).**
5. **TRITON_ATTN's 32k prefill loss is a hard-coded platform gate.** `unified_attention` has a `tuned_large_head` branch (BLOCK_M 32, 8 warps, KV tile 128) for exactly this shape — head_size 256, prefill — but it requires `current_platform.is_device_capability_family(100)`, i.e. NVIDIA Blackwell (VERIFIED, `triton_unified_attention.py:944`). On ROCm the path keeps BLOCK_M 16, and with `num_queries_per_kv` = 24/4 = 6 that means **BLOCK_Q = 2 query rows per program**, so the KV cache is re-read ~8192 times per layer. That is the 102.4 s (68.7%) attention cost. **Therefore: 32k prefill on vLLM cannot be fixed by configuration on this model; it needs a patched gate (INFERRED: enabling the branch on gfx12 is a 1-line source change worth testing).**
6. **Neither backend is good at both ends, and vLLM has no mixed mode.** ROCM_ATTN prefills ~2× faster; TRITON_ATTN decodes ~5× faster. vLLM selects one backend for all attention layers, so the choice is per-workload. At 32k the decode term dominates any realistic output length, so TRITON_ATTN wins the request by 2.7× (MEASURED). **Therefore: TRITON_ATTN is the recommendation until the prefill gate is patched.**
7. **Memory behaviour is clean and not a factor.** VRAM@load 27.0–27.1 GB, peak 30.6–30.8 GB at 32k, peak GTT ≤ 112 MiB against a ~77 MiB idle baseline → **no host-RAM spill** in any run (MEASURED). Memory clock pinned at 1258 MHz throughout; no throttling signature.
8. **The GDN Triton fallback is real but minor.** `fused_gdn_decode_post_conv_mtp` is not built for ROCm (log + source), so all 48 GDN layers take the Triton path; measured cost ~1.9 ms/token, ~3% of the step. **Therefore: do not chase the GDN kernel; it is not what separates vLLM from llama.cpp here.**

## Methodology & caveats

- **Harness:** llama-benchy 0.4.0 against the live server, `--exact-tg --no-cache --runs 3` (unique prompts from its Gutenberg corpus, so no prefix-cache inflation; prefix caching also disabled server-side). Warm-up request per shape, discarded by the tool.
- **Profiling:** vLLM's built-in torch profiler (`--profiler-config`, `/start_profile`/`/stop_profile`), `with_stack=false`. Requests sent as explicit token-ID lists with `min_tokens`/`ignore_eos` for exact shapes (512+64, 32768+32). The profiler config was present at boot for the benchmark runs but inactive until `/start_profile`; profiled step time (59.0 ms) is *below* the unprofiled equivalent (61.8 ms), so profiling did not inflate the timings.
- **Sampling:** `bench/lib/vram_sampler.py` at 1 s for the whole arm; windows cut by wall-clock to match each phase. `amd-smi metric -g 0 -u` sampled by hand during the 32k decode for GFX/UMC activity.
- **Sampler defaults:** the checkpoint's `generation_config.json` overrides vLLM defaults (temp 1.0, top_k 20, top_p 0.95); llama-benchy does not set them, so decode includes a 248320-vocab top-k/top-p sort (~0.37 ms/token, MEASURED).
- **Rule 16 (depth curve) not satisfied:** only two depths (512, 32768) were measured, per the user's stated shapes. No exponent/R² fit is reported, and no claim is made about intermediate depths.
- **Rule 6 gaps (stated, not worked around):** (a) `bench/` has no vLLM launcher — `serve_llamacpp.sh` is llama.cpp-only — so the root-level `start_vllm.sh` owns this; fold-in candidate `bench/engine-bench/serve_vllm.sh`. (b) `bench/lib/report.py` accepts only `results.jsonl` / `sweep-summary.json` / quality files, so it cannot chart llama-benchy JSON; **this report has no charts** (tables only, per the user's decision) and `report.py` should grow a `llama-benchy` kind. (c) The trace summariser is a one-off scratchpad script, not a repo tool; if kernel profiling recurs it belongs in `bench/lib/`.
- **One variable per comparison:** the two arms differ only in `--attention-backend` (same model, flags, env, launcher). Boot time differs because the first arm compiled the Triton/inductor caches.
- **Not tested:** concurrency (vLLM's actual strength), FP8, AWQ g32, prefix caching, and any llama.cpp re-measurement with llama-benchy for a like-for-like baseline.
