## Summary

Five tuning ideas from an internet forum post were tried against the served Qwen3.8-27B configuration (MTP with the default 3 draft tokens, f16 KV). None of them improves it.

- **Drafting deeper hurts on this output.** `--spec-draft-n-max 5` costs **−11% / −20% decode** (Welch t −6.2 / −4.8). The forum's MTP + ngram-mod recipe costs **−11%**. Adaptive MTP from PR #27210 costs **−15% / −5%** against the same build's plain MTP.
- **Why:** drafting past 3 tokens raises the cost of each verify step by ~39% (54 → 75 ms, MEASURED). Prose-like reasoning output raises tokens per step by only 12–23%.
- **`rm_kq=1` is a tie** (+0.4% decode). On RDNA4 it can only reach the Q6_K/Q3_K slice (17%) of this model's weights.
- **q8_0 KV ties f16** on prefill and decode up to 18.4k tokens of context, and saves **4.8 GB** of VRAM. The forum's "f16 gives much better prefill" did not reproduce on b10909 at that depth.
- **Caveat:** benchy's output shape is reasoning prose. The ideas built for repetitive output (ngram-mod, adaptive depth) remain untested on code.

## Consequences & root causes

1. **Drafting past 3 tokens costs more per step than it wins on this output.** MEASURED, derived as `1000·τ/decode`:
   - A verify step costs 53.8–55.4 ms with 3 drafts, 50.9 ms with 2, **75.3 ms with 5** and 72.4 ms under adaptive (τ ≈ 3.4) at depth 0. Depth 16384 shows the same pattern.
   - Going from 3 to 5 drafts adds **+39% per step**, while τ rises only +23% (2.87 → 3.54) at depth 0 and +12% (2.94 → 3.28) at 16k.

   The break-even is simple arithmetic (INFERRED): with τ ≈ 1 + n·p, five drafts need an average acceptance of p ≥ ~0.60 (τ ≥ ~4.0) to match three. Measured: 0.51 at depth 0 and 0.45 at 16k.

   **Therefore:** keep `--spec-draft-n-max` at its default of 3 for reasoning and prose. Deeper drafting can only pay on output with ≥ 60% average acceptance at 5 drafts, meaning copy- or recall-heavy code. That is untested here (OPEN).

   Why the step cost jumps nonlinearly (+3 ms for 2 → 3 drafts, +21 ms for 3 → 5) is **OPEN**. Two candidates (INFERRED, not tested):
   - the Vulkan mat-vec shaders switch configuration above 4 columns on RDNA3-class devices (`ggml-vulkan.cpp:5476-5480`, `rm_int_n`). A 6-token verify crosses that line; a 4-token verify does not.
   - per-position recurrent-state snapshots in the Gated-DeltaNet layers scale with draft length.
2. **Adaptive MTP (PR #27210) loses on this output for the same reason.** On prose-like reasoning its climb rule still took the depth above 3 (τ 3.40 / 3.48 vs 3.08 / 2.84 on the control), so it paid the ~72 ms step: **−15.5% / −4.8% decode**.
   - This is consistent with the author's own R9700 numbers (CLAIMED, below): reasoning 51.68 → 51.42, prose 55.89 → 56.64. The gains are on code (+12.6%) and recall (+80%), which this campaign does not exercise.
   - It also costs **+1316 MiB VRAM at load** (31502 vs 30186 on the same build; MEASURED). That is ≈ 146 MiB per extra draft slot (INFERRED from 9 extra slots), against a CLAIMED ~250 MB/slot.
   - Peak 31711 of 32624 MiB leaves **913 MiB of headroom**. **Therefore:** n-max 12 at f16 / 163840 sits at the VRAM edge on this card with a desktop session. Test it on code before adopting; it needs q8_0 KV or a smaller ctx to be safe.
3. **The forum's MTP + ngram-mod recipe is −11%, but it changes two knobs at once:** ngram-mod, and `--spec-draft-n-max 2` instead of 3.
   - τ fell to 2.40 / 2.52; the cap with 2 drafts is 3.
   - With `--spec-ngram-mod-n-min 24`, an n-gram draft is used only when ≥ 24 tokens match verbatim. That is rare in fresh reasoning prose (INFERRED), so the arm behaves mostly like MTP with 2 drafts.
   - This agrees with the repo's earlier hipfire finding that model-free n-gram drafting gives τ ≈ 10 on copy-heavy output and nothing on prose (MEASURED 2026-09-10, benchmark-results skill rule 17).
   - **Therefore:** reject it for general use. Its niche is edit/copy-heavy agent turns, untested here (OPEN).
4. **q8_0 KV has no prefill penalty on b10909 up to 18.4k tokens.** Against the repeat baseline: +2.5% at depth 0, +1.0% at 16k. Decode −1.5% / −3.7% (|t| < 1, tie). **4799 MiB less VRAM at load** (MEASURED). So the forum's "much better prefill with f16" does not reproduce here.
   - A plausible reason is that the forum measurement predates the llama.cpp #25494 fix (coopmat1 dequantised q8_0 KV 32× per prefill). Our builds carry it since 6fdd0ac, per `~/.config/llama-swap/generate.py`; the forum post names no build (INFERRED).
   - **Depth caveat (CLAUDE.md rule 16 / skill rule 12):** this is one point at 18.4k. The 2026-09-10 four-depth curve (Vulkan/RADV, then-current build) measured f16 −0.294 vs q8_0 −0.499 prefill decay: f16 +5.6% at 18k and +40% at 73k.
   - At 18k our point shows no f16 advantage, so the two measurements disagree there (**OPEN**: re-measure the f16/q8_0 depth curve on b10909).
   - **Therefore:** until then, keep f16 on the 163840 row for deep-context prefill. The q8_0 row's 225k window stays a deliberate trade of VRAM for window.
5. **`rm_kq=1` cannot matter much on RDNA4 with this model.**
   - On AMD, the integer-dot MMVQ path handles Q4_K/Q5_K mat-vec when k ≥ 2048 (`ggml_vk_should_use_mmvq`, `ggml-vulkan.cpp:9740-9749`). That path uses `rm_kq_int`, not `rm_kq`.
   - Q6_K is excluded from MMVQ on every non-Intel GPU (`:9712-9714`). Only Q6_K/Q3_K, **17.0% of this model's weight bytes** (MEASURED), take the `rm_kq` path (VERIFIED-IN-SOURCE).
   - Even a few percent on that slice bounds the total at about half a percent. Measured: +0.42% decode, tie.
   - The CLAIMED large gain in discussion #21043 is an **AMDVLK** result (+13% dense); its RADV figure is +1%. We run RADV. **Therefore:** don't carry the patch. `build/b10909-rmkq1-vulkan` stays built, unpromoted.
6. **OPEN — prefill of the first two arms is low, and time-ordered.**
   - Depth-0 prefill was 715 (arm 1) and 739 (arm 2) vs 783–803 for arms 3–7. That is a TTFT excess of ~0.2–0.25 s on a 2.6 s request.
   - The identical baseline configuration repeated 20 min later gave +9.5% (t 6.6): real, not sampling noise.
   - Arm 1 also had the lowest average power (189 W vs 193–203 W). Arms 1–2 started within minutes of two Vulkan builds finishing on the same CPU.
   - Root cause not established.
   - **Consequence:** prefill differences under ~10% between arms in this campaign are not attributable. Decode reproduced within −0.4% / +1.2% and carries the verdicts.
7. **OPEN — every loaded server holds ~1.5 GB of GTT.** The first sample after load was 1507 MiB and peaks were 1630–1702 MiB, against **60 MB idle** (read after the campaign).
   - It is not a VRAM-pressure spill (MEASURED): the q8_0 arm had ~7 GB of VRAM free and held the same 1638 MiB of GTT.
   - The production llama-swap q8_0 row showed 2111 MB of GTT the same afternoon.
   - Most likely host-visible or pinned Vulkan buffers (INFERRED; exact attribution OPEN, since load-time buffer lines are not printed at the default log level).
   - No arm showed rising GTT during a run.
8. **Decode figures are comparable across arms (skill rule 16).** 512 generated tokens per request. The memory clock sat at ≥ 1200 MHz in 93.7–96.6% of busy samples in every arm, so no low-memory-clock episode like the 2026-09-10 hipfire runs occurred.

## Methodology & caveats

- **Workload:** llama-benchy 0.4.0, streaming chat completions.
  - Prompt: a random slice of Project Gutenberg #1661 (Sherlock Holmes), tokenized with the `Qwen/Qwen3.8-27B` tokenizer (HF, commit `1d4bf0f`).
  - 2048 prompt tokens, plus 16384 depth tokens as a system message. 512 forced output tokens (`--exact-tg` → `ignore_eos`).
  - `--no-cache` sends `cache_prompt=false`, so every request is a cold prefill.
  - Per test, one warmup request is dropped and 3 timed runs are kept. benchy sends no sampler parameters, so the server's CLI sampler applies.
- **Isolation:**
  - A fresh server per arm (`bench/engine-bench/serve_llamacpp.sh`, port 8095), preceded by `bench/lib/gpu_exclusive.sh 28000` (≥ 28000 MiB free).
  - llama-swap was stopped for the whole campaign and restarted afterwards.
  - VRAM/GTT/power/clocks were sampled at 1 s by `vram_sampler.py` (via `engine-bench/run.sh SAMPLE_VRAM=1`).
- **MTP stats:** from the server log `draft acceptance … mean len` line of each request. There are 9 per arm: a coherence request, then per depth 1 warmup + 3 timed. Only the timed requests are used. Per-position acceptance is not printed at the default verbosity.
- **Limits:**
  - **Two depths (≤ 18.4k tokens) is a screening, not a depth curve** (CLAUDE.md rule 16). No decay exponents; nothing here speaks for 64k+.
  - n=3 per cell.
  - One output shape (reasoning prose about book text), not the coding output the served row is for. Speculation results depend on output shape (skill rule 17).
  - No MTP-off arm, so MTP's own gain is not measured here.
  - The forum's ngram recipe varies two knobs.
  - The `rm_kq` A/B is llama-bench without MTP: its effect is below benchy's decode noise (sd up to 6 t/s at 16k).
- **Short-iteration budget:** each arm took 203–296 s including server load (user budget: 3–4 min per iteration).
