# Benchmark: 35B-A3B serving combos — backend × MTP × KV × depth × concurrency — R9700 (gfx1201)

- **Date:** 2026-07-11 18:44 · **Track:** engine-bench campaign (`campaign.sh`, resumable matrix)
- **GPU/Host:** AMD Radeon AI PRO R9700, 32624 MiB · `HSA_OVERRIDE_GFX_VERSION=12.0.1` · ROCm-SMI 7.8.0
- **Runtimes/builds:** llama.cpp **b9950-961e4b26a** — ROCm (`bench/llamacpp/`) + Vulkan/RADV (`bench/llamacpp-vulkan/`), via `serve_llamacpp.sh`
- **Models:** `Qwen3.6-35B-A3B-UD-Q4_K_M.gguf` (embedded MTP layer) · base knobs `-ub 2048 -b 8192 -fa on -c 65536 -ngl 99`
- **Data:** `bench/runs/2026-07-11-1844-campaign-combo35b/` — 16 server configs, 232 rows (176 request + 56 aggregate), `failures.txt`, per-config `servers/*.{cmdline,props.json}`

## Summary

Full 2×2×2 matrix (backend × MTP × KV) validated at the real serving operating point on code
workloads. **MTP is a large single-stream win — +30–40 % decode** (Vulkan cr8000 104.7 → 139.4
tok/s; thinking 108.9 → 132.4) — **but it *reverses* under concurrency**, costing −8 to −15 %
per-stream and lower aggregate at 4 slots, because speculative drafting contends with the parallel
slots. **q8_0 KV gives no decode benefit and a small prefill penalty** at these depths (confirms the
sweep's KEEP-f16 verdict on the served path). Under load, **per-stream decode falls ~2.2× from c1→c4
(Vulkan 104→48) while TTFT p95 rises ~4× (2.7→11.3 s)**, and all 4 streams fit in 32 GB. The
**`cr64000` point failed on all 8 configs** — a reproducible context-overflow finding, not flakiness:
the ~65 K-token prompt leaves no generation headroom in the 65 536 window. **New winning config for
interactive single-stream: llama.cpp Vulkan + MTP + f16 KV ≈ 140 tok/s decode; for parallel agentic
serving, MTP off.**

## Results — single stream (concurrency 1, MEASURED)

`cr8000`/`cr32000` = code-review (completions api, `PREFIX_MODE=unique`); `thinking` = chat api,
1024-tok budget, MEASURED `ttfa_s`. Prefill = p50 tok/s, Decode = per-stream tok/s p50.

| Config | KV | MTP | cr8000 pf / dec | cr32000 pf / dec | thinking dec / ttfa |
|--------|:--:|:---:|----------------:|-----------------:|--------------------:|
| **vulkan** | f16 | **1** | 2786 / **139.4** | 2410 / **116.9** | **132.4** / 0.30 s |
| vulkan | q8_0 | 1 | 2643 / 139.9 | 2021 / 109.7 | 128.6 / 0.31 s |
| vulkan | f16 | 0 | 3044 / 104.7 | 2605 / 95.5 | 108.9 / 0.30 s |
| vulkan | q8_0 | 0 | 2858 / 103.0 | 2176 / 97.2 | 106.6 / 0.29 s |
| rocm | f16 | 1 | 2493 / 95.7 | 2062 / 72.0 | 88.8 / 0.36 s |
| rocm | q8_0 | 1 | 2909 / 81.1 | 2086 / 81.5 | 86.4 / 0.34 s |
| rocm | f16 | 0 | 3207 / 73.5 | 2228 / 58.4 | 74.8 / 0.30 s |
| rocm | q8_0 | 0 | 3361 / 69.6 | 2282 / 61.4 | 73.2 / 0.29 s |

**FAILED (all 8 configs):** `cr64000` → *"no tokens received"*. Cause: fixture ≈ 65 019 real
tokens (measured 3.58 chars/tok from the 8 K/32 K points) vs server `-c 65536`, leaving < 256 tokens
for generation → the server rejects the request. **A finding, not a gap:** 64 K depth on this model
needs `-c` > 65536 + generation budget (and f16 KV then approaches the 32 GB ceiling — this is the
regime where q8_0 KV finally earns its place). Kept in `failures.txt`, never averaged away.

## MTP interaction — the headline (MEASURED, Δ decode)

| Backend / KV | Single stream (cr8000) | 2 streams (agentic-c2) | 4 streams (agentic-c4) |
|--------------|-----------------------:|-----------------------:|-----------------------:|
| vulkan / f16 | 104.7 → **139.4 (+33 %)** | 78.3 → 88.5 (+13 %) | 47.5 → **43.5 (−8 %)** |
| rocm / f16 | 73.5 → **95.7 (+30 %)** | 55.3 → 69.5 (+26 %) | 44.5 → **38.0 (−15 %)** |

MTP's per-stream speedup **shrinks as concurrency rises and goes negative by c4** (aggregate tok/s
also lower with MTP at c4: Vulkan 59.0 → 54.7, ROCm 61.5 → 58.6). **Rule of thumb: MTP on for
interactive/single-user, MTP off for parallel agent fleets.**

## KV decision on the served path (confirms the sweep)

| Backend | Metric | f16 | q8_0 | Δ | Read |
|---------|--------|----:|-----:|--:|------|
| vulkan/mtp1 | cr8000 decode | 139.4 | 139.9 | +0.4 % | tie — no decode benefit |
| vulkan/mtp0 | cr8000 prefill | 3044 | 2858 | −6.1 % | prefill penalty (worse at longer ctx, cf. sweep −29.7 % @32K) |
| rocm/mtp0 | cr8000 decode | 73.5 | 69.6 | −5.3 % | decode penalty |

Same verdict as the sweep: **keep f16** at these depths — q8_0 costs prefill (Vulkan) or decode
(ROCm) and returns no decode gain. Its value is purely context-headroom near/above 64 K.

## Concurrency scaling — agentic (4 slots, per-slot ctx = 65536/4 ≈ 16 K)

Best parallel config **vulkan / MTP off / f16** (agentic-8000 variants, unique prefix, reps=2):

| Concurrency | Decode/stream p50 | TTFT p50 / p95 | Aggregate tok/s | n_ok |
|------------:|------------------:|---------------:|----------------:|-----:|
| 1 | 104.2 | 2.7 / 2.7 s | 50.0 | 2 |
| 2 | 78.3 | 5.3 / 5.3 s | 45.4 | 4 |
| 4 | 47.5 | 10.6 / 11.3 s | 59.0 | 8 |

Per-stream decode falls **2.2×** from c1→c4 while TTFT p95 rises **4.2×** — expected as 4 slots
share compute. All 8 requests succeeded; **the R9700 serves 4 parallel 35B agents inside 32 GB**
at ~48 tok/s/stream and ~11 s TTFT. (Aggregate tok/s is prefill-dominated here — short ~40–50-token
generations — so read decode/stream + TTFT as the load story, not aggregate.)

## What moved the needle

| Change | Effect | Note |
|--------|--------|------|
| ROCm → **Vulkan** | decode +42 % single-stream (73.5 → 104.7, mtp0 cr8000) | Vulkan is the base backend |
| **MTP on** (single stream) | **+30–40 % decode** | biggest served lever; reverses at c4 |
| MTP on (4 streams) | **−8 to −15 % decode** | turn MTP off for parallel serving |
| f16 → q8_0 KV | ~0 decode, −6 % prefill (Vulkan) | keep f16 until ctx forces it |
| depth 8K → 32K | decode −16 % (Vulkan 104.7 → 95.5), prefill −14 % | expected KV growth |

## Recommended config (from this campaign)

```
# Interactive / single-user — max decode:
llama-server -m Qwen3.6-35B-A3B-UD-Q4_K_M.gguf -ngl 99 -fa on -ub 2048 -b 4096 \
  -ctk f16 -ctv f16 -c 65536 --spec-type draft-mtp        # Vulkan build, MTP on → ~140 tok/s decode

# Parallel agent fleet (4 slots) — MTP OFF:
llama-server -m Qwen3.6-35B-A3B-UD-Q4_K_M.gguf -ngl 99 -fa on -ub 2048 -b 4096 \
  -ctk f16 -ctv f16 -c 65536 -np 4                          # Vulkan build → ~48 tok/s/stream, 4 agents in 32 GB
```

For 64 K+ single-context prompts, raise `-c` above the prompt length + generation budget; f16 KV
then nears the 32 GB ceiling, which is where q8_0 KV becomes worth its prefill cost.

## Methodology & caveats

- **Real prompts** from the tracked corpus (TS + Python), token-counts server-reported
  (`tok_count_source=usage`); code-review via `/v1/completions`, thinking via `/v1/chat/completions`
  (chat template — raw completions EOS instantly on this instruct model). `PREFIX_MODE=unique`
  everywhere (cold prefill; identical prompts inflate prefill 2.4× from request 2 — measured).
- reps=2 (engine-bench); ±3 % noise band. Servers restarted per config via `serve_llamacpp.sh`
  (exact cmdline + `/props` archived in `servers/`). Part A = NP 1 depth curve + thinking; Part B =
  NP 4 concurrency 1/2/4.
- **Failures kept**: `cr64000` overflow (8×) is in `failures.txt` and this report, not silenced.
- Per-point VRAM was **not** sampled in this campaign run (the sweep run measured f16 peaks of
  25–27 GiB at 32 K, 224–235 W, no throttling — headroom is consistent with all NP≤4 configs fitting).
- Provenance: every number here is `MEASURED` from `bench/runs/2026-07-11-1844-campaign-combo35b/`.
