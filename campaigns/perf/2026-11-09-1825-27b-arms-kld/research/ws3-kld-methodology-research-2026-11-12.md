## Q1. How llama-perplexity --kl-divergence works, and what values people report
---------------------------------------------------------------------

### 1.1 Mechanics (T1)
- Two-pass: `--kl-divergence-base FILE` saves the reference logits over a text corpus (conventionally wikitext-2 test); `--kl-divergence --kl-divergence-base FILE` scores the other model against it. CLAIMED (https://github.com/ggml-org/llama.cpp/blob/master/tools/perplexity/README.md).
- Full vocabulary, no top-k: the base file stores, per token, ALL n_vocab logits as uint16, linearly scaled per token with the range clamped to 16 nats below the max (`min_logit = max(min_logit, max_logit - 16)`), plus a float scale and min. In the KL loop, base probabilities whose log-prob is <= -16 are skipped (`if (p_log_base > -16.f)`), accumulators are `double`. CLAIMED (https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/perplexity/perplexity.cpp).
  - Consequence (INFERRED): the base file is itself lossy. The README says so: the "f16" row (reference f16 scored against its own stored logits) gives KLD 0.000551 on LLaMA-3-8B, "the difference resulting only from this downcast". CLAIMED (README above). That 5.5e-4 is a storage floor that is part of every number in the README's table. Also, tokens with p < e^-16 (~1.1e-7) contribute nothing; negligible for mean KLD.
- Stats printed (final block only if >= 100 tokens): Mean PPL(Q)/PPL(base), Cor(ln PPL), mean ln(PPL ratio); Mean KLD, Maximum, 99.9 / 99 / 95 / 90 %, Median, 10 / 5 / 1 / 0.1 %, Minimum KLD; Mean Δp, percentiles of Δp, RMS Δp, and "Same top p". CLAIMED (perplexity.cpp above).
  - Δp = P_quant(correct corpus token) - P_base(correct corpus token), i.e. a statistic on the ground-truth next token, not on the whole distribution. CLAIMED (perplexity.cpp).
  - "Same top p" = fraction of positions where argmax(quant) == argmax(base), i.e. top-1 agreement. CLAIMED (README).
  - Uncertainty on the mean KLD: standard error assuming per-token KLD is i.i.d. Gaussian (`sqrt(var/(count-1))`); Same-top-p: Gaussian approx of binomial. CLAIMED (README + perplexity.cpp). INFERRED: both assumptions are wrong in practice (per-token KLD is extremely right-skewed, mean/median ~ 20x, and tokens in one chunk are correlated), so these "±" are optimistically narrow; this is the same point our cluster bootstrap addresses.
- Important for comparison with our method: llama-perplexity scores the quant on NATURAL corpus text (teacher-forced on the corpus, base also teacher-forced on the corpus), not on the reference's own generated continuation, and only the second half of each chunk is scored in practice (INFERRED from https://smcleod.net/2026/04/measuring-model-quantisation-quality-with-kl-divergence/ which says it matches llama.cpp's convention; Unsloth says "Most GGUFs are evaluated on Wiki-test with 512 context windows", https://unsloth.ai/docs/models/qwen3.5/gguf-benchmarks).

## Q2. Top-k truncated KL vs full-vocabulary KL
---------------------------------------------------------------------

### 2.1 Is our estimator a lower bound? (INFERRED, standard information theory)
- Coarse-graining: for any partition of the vocabulary, KL of the induced distributions <= full KL (data-processing / log-sum inequality, Cover & Thomas). So the exact quantity  sum_{t in R} p_t ln(p_t/a_t) + r_tail ln(r_tail/a_tail),  with R = ref top-20, tail = everything else for BOTH distributions, is a rigorous lower bound on full KL.
- Our estimator (per the module docstring) uses a_t = arm logprob of t, floored at the arm's minimum top-20 logprob when t is absent, and a_tail = 1 - sum(arm top-20), where the arm's top-20 SET is not R. Two deviations from the exact partition, with opposite signs:
  (a) missing-token floor: the true arm logprob of a token outside its top-20 is <= the arm's min top-20 logprob, so the floored term UNDER-estimates (-> lower bound, fine);
  (b) tail bucket built from the arm's own top-20: when the sets differ (m tokens in arm-top20 but not ref-top20), 1 - sum(arm top-20) is <= the true arm mass outside R, so ln(r_tail/a_tail) is OVER-estimated.
  Net: not a strict lower bound when top-20 sets differ; the error is small when sets mostly coincide (the typical case) and both effects scale with m. The clamp at 0 is a symptom: individual terms are not guaranteed to sum to >= 0 under mismatched partitions, and clamping makes the noise-only estimator one-sided (E[max(0, noise)] > 0 even when true KL = 0), which positively biases self-run floors and small differences. Recommendation below.
- The tightest published variant is "the minimum KL consistent with the stored top-k lists", i.e. solve for the arm distribution that minimises KL subject to its known top-k values and total mass; explicitly a lower bound on full-vocabulary KL, used with top-200 and mean reference tail mass 0.0025. CLAIMED (https://prismix.dev/news/4d0aff670c11, T3).
- A published alternative: renormalise each side over its own top-k, sum over the reference support, floor missing tokens at log-prob -10 (they call it a "floor cmin = -10"). Top-k=20 vs top-60 vs full set give the same correlation with benchmark scores (rho -0.73 for both k=20 and k=60 on Qwen3.6-35B-A3B). CLAIMED (https://arxiv.org/pdf/2606.19558, Nikolic et al., Appendix B / Table 3, T2 preprint; read via pdftotext).

### 2.2 How large is the bias? (CLAIMED data, INFERRED extrapolation)
- Sparse top-K cache vs dense, with the tail lumped into one scalar: mean KLD biased LOW by -6.63 % (K=64), -5.30 % (128), -4.05 % (256), -3.10 % (512), -2.31 % (1024); "rank-preserving" across six models. 10-prompt subset, one 4-bit comparison model. CLAIMED (https://smcleod.net/2026/04/measuring-model-quantisation-quality-with-kl-divergence/, T3). Author: "lumping the tail into one bin introduces a small rank-preserving underestimate".
- Extrapolating that trend (~ -1.3 percentage points per halving of K) to K=20 gives about -9 % for a mean KLD around 0.1, INFERRED, and it is for a different tool, model and bit-width than ours; treat as "roughly -5 to -15 %, same sign" and not as a correction factor.
- Tail mass sizes: top-16 covers 99 % of the distribution on Llama-3.1-8B (CLAIMED https://fireworks.ai/research/llm-quantization-quality-kl-divergence, T2 vendor blog); mean reference tail mass beyond top-200 = 0.0025 on Qwen3.6-27B agentic text (CLAIMED prismix link above). INFERRED: tail mass beyond top-20 on code/prose continuations is a few tenths of a percent on average but is heavy-tailed (high-entropy positions put 10-50 % outside top-20), and those are exactly the positions that dominate the mean KL.
- INFERRED: bias is larger (a) for lossier arms (more mass moved outside the reference top-20), and (b) in the tail statistics (p99+) than in the mean. Ranking-preservation is observed (smcleod) but not guaranteed; the floor-and-bucket scheme can mis-rank two arms that differ mainly in how they place tail mass.
- Distillation literature agrees on structure, not size: KL splits exactly into top-K term + alpha_tail * KL(normalised tail), and the tail term is "non-trivially different from zero" (https://arxiv.org/html/2602.20816v1, T2; no numbers). Tail mass "decays sharply beyond K >~ 5-10" (same).

### 2.3 What serving-engine tools can return
- vLLM: `max_logprobs` default 20 (matches OpenAI), `-1` = no cap ("may cause OOM"); applies to `logprobs` and `prompt_logprobs`. CLAIMED (https://docs.vllm.ai/en/stable/api/vllm/config/model/, https://docs.vllm.ai/en/stable/cli/serve/; T1). So a vLLM arm can supply more than top-20 if started with `--max-logprobs`, but the reference side was the binding constraint (llama.cpp server `n_probs`; no hard cap documented, https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md T1).
- vLLM prompt_logprobs ignore the prefix cache (the engine recomputes the full prompt) and are not cached. CLAIMED (https://docs.vllm.ai/en/stable/usage/v1_guide/).
- Other KLD tools found: llama.cpp (full vocab, above); mlx-kld (top-K cache, K=256 default, https://smcleod.net/... above); Fireworks (reference-sampled completions, quant teacher-forced, N=16 renormalised, https://fireworks.ai/research/llm-quantization-quality-kl-divergence); a r/LocalLLaMA vLLM+llama.cpp benchmark (top-200 minimum-KL lower bound); localbench (top-40, patched llama.cpp). I did not find a vLLM-project or SGLang-project KLD script; SGLang's deterministic-inference docs exist (https://docs.sglang.io/advanced_features/deterministic_inference.html) but I did not verify any KL tooling there.

## Q3. Cross-engine pitfalls and self-KLD floors
---------------------------------------------------------------------

### 3.1 Tokenisation / detokenisation / special tokens
- Key distributions by TOKEN ID, never by decoded string. Our own collision bug (two different ids rendering the same string) is the generic failure. vLLM can return ids: `--return-tokens-as-token-ids` renders tokens as `"token_id:{id}"` (CLAIMED https://docs.vllm.ai/en/stable/cli/serve/); llama.cpp server returns `id`, `token`, `bytes` per entry (CLAIMED https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md). INFERRED: byte-fallback tokens (partial UTF-8) detokenise differently per engine, so ids/bytes are the only safe join key; where an engine only gives strings, assert uniqueness within each top-20 list and drop/flag positions with collisions.
- A KLD tool bug of the same family was found by another author: cached references were re-tokenised, silently invalidating all comparisons; fix = reuse cached reference token ids verbatim (CLAIMED https://smcleod.net/2026/04/measuring-model-quantisation-quality-with-kl-divergence/). Self-comparison must return exactly 0, use it as a unit test.
- Special tokens / templates: chat templates differ between engine families and break prompt identity; raw text without template (our choice) avoids it. BOS/`add_special` handling and `<think>` rendering are the other classic divergences (INFERRED; not found as documented KLD pitfalls in a source).

### 3.2 Raw vs processed logprobs
- vLLM `--logprobs-mode`: `raw_logprobs` (default) = "values before applying any logit processors, like bad words"; `processed_logprobs` = "after applying all processors, including temperature and top_k/top_p"; plus `raw_logits` / `processed_logits`. "the returned logprobs do not reflect the final adjusted probabilities used during sampling". For `prompt_logprobs` raw and processed are identical. CLAIMED (https://docs.vllm.ai/en/stable/cli/serve/, https://docs.vllm.ai/en/stable/usage/v1_guide/; T1). INFERRED: a KLD run must pin `raw_logprobs` on every vLLM arm (default, but pin it and record it), since processed mode at temp 0 / top-k would renormalise or collapse the distribution.
- llama.cpp server: `n_probs` gives top-N "given the sampling settings"; `post_sampling_probs=true` switches to post-chain probabilities; default presumably pre-chain, and the README does not document behaviour at temperature exactly 0 (CLAIMED + gap, https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md). INFERRED: verify per arm that exp(top-20 logprobs) sums to <= 1 and that the argmax token's logprob does not equal 0 (a degenerate post-sampler value) before trusting; our selftest (logprobs20 / raw_logprobs flags) already does part of this.
- Radiance logprob semantics: not found in any external source; local audit file (09-...) was empty at the time of this research, so unverified here.

### 3.3 Batch invariance and nondeterminism
- Root cause is lack of batch invariance, not atomics: kernel results depend on batch shape and server load. On Qwen3-235B-A22B at temp 0, 1000 completions of 1000 tokens gave 80 unique outputs, first divergence at token 103; with batch-invariant kernels all 1000 identical. CLAIMED (https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/, T2). Bitwise-matched sampler/trainer gives KL exactly 0; unmatched implementations of the same weights gave sampler-trainer KL about 0.001 with occasional spikes (same source).
- vLLM batch-invariant mode: `VLLM_BATCH_INVARIANT=1`, beta; deterministic kernels, disables optimisations that may be non-deterministic, with a performance cost; hardware list includes AMD Instinct (gfx90a, gfx942, gfx950) and does not list RDNA4/gfx1201. CLAIMED (https://docs.vllm.ai/en/stable/features/batch_invariance/, T1). INFERRED: unsupported on our R9700, so vLLM arms carry run-to-run and batch-shape noise we cannot switch off; measure it (self-run) instead.
- SGLang deterministic mode (`--enable-deterministic-inference`) exists (FlashInfer/FA3/Triton backends; 34 % avg slowdown per a secondary blog, up to 56 % per an arXiv preprint). CLAIMED (https://docs.sglang.io/advanced_features/deterministic_inference.html, https://arxiv.org/pdf/2601.17768v2). Not applicable to our engines.
- llama.cpp: server docs state outright that logits are "not guaranteed to be bit-for-bit identical for different batch sizes (prompt processing vs. token generation)" and `cache_prompt` (default true) "can cause nondeterministic results". CLAIMED (https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md, T1). A 2026 preprint on llama.cpp (Qwen2.5-7B) found: with prefix reuse off, repeated runs reproduce every token and logprob; with it on, 37.4 % (16-bit) to 82.5 % (4-bit) of episodes diverged, and 4-bit weights through 16-bit kernels showed no extra effect, placing the amplification in the quantised kernels (CLAIMED https://deeplearn.org/arxiv/844864/same-request,-different-answer:-quantization-amplifies-cache-induced-divergence-in-llm-serving, T3 aggregator). INFERRED: every llama.cpp KLD request must set `cache_prompt: false` (or equal cache state for ref and arm), and `-b/-ub` must be recorded and held equal.
- Vulkan vs ROCm: no source found that publishes cross-backend KLD (searches returned only speed comparisons). An unverified search snippet cited a 0.00043 nats Vulkan-vs-CPU mean KL on a llama.cpp discussion (https://github.com/ggml-org/llama.cpp/discussions/10879); I could not locate the comment on the page; treat as unverified.

### 3.4 Teacher-forced prefill vs incremental decode
- Quantised Metal backend: scoring the same context with the last 5 tokens in one batch vs one at a time shifts logits by up to ~0.1 and flips argmax at near-ties (top-1/top-2 gaps 1.8e-3 to 5.8e-3); fp32 CPU is batch-invariant. CLAIMED (https://arxiv.org/pdf/2607.17283, Chordiya, T3 preprint; read via pdftotext).
- vLLM docs: "Changes in batch size may cause variations in logprobs and output probabilities" and "does not currently guarantee stable token log probabilities". CLAIMED (https://docs.vllm.ai/en/stable/features/speculative_decoding/, T1).
- INFERRED for our design: the reference's top-20 are produced during incremental decode (batch 1, one token) while the arms are scored on a teacher-forced pass (multi-token batch). Different kernels (GEMV vs GEMM, flash-attn shapes) => q8f, which re-runs the same engine, only captures this if it is run in exactly the same two modes (ref-decode vs arm-teacher-forced). Check that q8f was produced by that path; if q8f is decode-vs-decode, the true floor for the teacher-forced arms is higher.

## Q4. Which summary statistics support "which quant / engine should I run"
---------------------------------------------------------------------

- Mean KLD: the expected information lost per token; additive over positions; the right quantity for expected log-loss and the one all published tables lead with. But dominated by few positions (Q3 table: mean/median ~ 20x for 8-bit; max 21 nats). CLAIMED (https://smcleod.net/... in 1.2).
- Median: robust "typical position"; says nothing about rare catastrophic positions; for near-lossless quants it is ~ the numerical-noise level (e.g. 3e-4 to 6e-4 for 8-bit above). Use for "is typical behaviour affected".
- p99 / p99.9 / max: where flips and failures live; Unsloth leads with 99.9 % KLD and adds Maximum KLD "for massive outliers" (https://unsloth.ai/docs/models/qwen3.5/gguf-benchmarks). INFERRED: with 4096 scored positions, p99.9 is 4 positions: report p99 and the share of total KL from the top 1 % of positions instead.
- Top-1 agreement ("Same top p"): direct, interpretable greedy-flip rate. INFERRED: with per-token flip rate f, P(no divergence in n greedy tokens) = (1-f)^n; f = 0.5 % gives 8 % survival at n = 512, so first-divergent position in our greedy pairing is a monotone transform of the same information. It ignores magnitude (a near-tie flip counts like a catastrophic one).
- dPPL / dNLL: weakest on ground truth that is not the model's own output; insensitive between close quants (PPL identical for Q5_0/Q5_1/Q5_K_S at 7.43 while GSM8K ranged 75.66-79.08, https://arxiv.org/html/2601.14277v1, T2).
- Does KLD predict task quality? Across the full range yes; in the near-baseline "silent zone" no. Qwen3.6-35B-A3B cohort: full-cohort rho(KLD, composite) = -0.72, silent zone (17 models with KLD <= 0.064) rho = +0.00; Devstral-24B: -0.86 full, -0.24 (p = 0.36) in the silent zone (KLD <= 0.027); the collapse holds for mean, median, p90, p99, dPPL, top-1 agreement, long context and response-only KLD (|rho| <= 0.25 across 14 variants). Per-prompt KLD separates failed vs passed LiveCodeBench prompts only weakly (geometric-mean ratio 1.08-1.22). CLAIMED (https://arxiv.org/pdf/2606.19558, T2 preprint, thresholds are cohort-specific and "descriptive"). Related: KL between baseline and compressed outputs tracks "flips" (Spearman 0.981 on MMLU) while accuracy can stay within 2 % of baseline with 5-13.6 % flips (CLAIMED https://arxiv.org/html/2407.09141v1 and Liner review, T2).
- Unsloth itself says PPL/KLD "can be misleading" and are "highly influenced by calibration" (https://unsloth.ai/docs/models/qwen3.5/gguf-benchmarks).
- Interpretation bands used by others (rules of thumb, not standards): < 1e-4 identical; 1e-3 to 5e-3 "typical well-made 6-bit"; 1e-2 to 5e-2 "typical 4-bit territory" (https://smcleod.net/... , T3); Fireworks: < 0.007 "generally high quality" (T2).
- Paired differences: INFERRED and standard: KL(a)-KL(b) on identical positions cancels the shared position-difficulty variance (the dominant source of variance since a few high-entropy positions carry the mean), so paired CIs are much tighter than the difference of two unpaired CIs. Evidence that unpaired is insufficient: two Q4 GGUFs at 0.2218 vs 0.2273 have "heavily overlapping intervals" (https://prismix.dev/news/4d0aff670c11, T3); other KLD tools publish no CI at all (smcleod says paired bootstrap on per-position differences is future work).
- How many prompts / tokens:
  - llama.cpp prints the final stats only at >= 100 tokens, and its standard error assumes i.i.d. Gaussian (perplexity.cpp).
  - 65,536 tokens (32x2048) "makes close pairs more stable but not CI-backed"; a ~50-prompt short mode "reversed or inflated several differences" (oQ6 beat RTN-6 by ~14 % short vs the reverse by ~3 % long; oQ4 vs RTN-4 16 % -> 3 %) and its 8-bit mean was 1.6e-3, which the author attributes to early-context-only scoring. CLAIMED (https://smcleod.net/...). 
  - INFERRED (our design): 128 prompts x 32 positions = 4096 positions; with within-prompt correlation rho ~ 0.3 (the repo's own research note estimate, unverified here) the design effect is 1 + 31*0.3 ~ 10, so n_eff ~ 400. For a metric with mean/median ~ 1000 (q8f) the CV of per-position KL is >> 1, so a CI half-width of tens of percent of the mean is expected. More prompts beat more positions per prompt; report the cluster-bootstrap CI of the PAIRED difference, not of each arm.

Recommended decision stat set (INFERRED): primary = paired mean KLD difference with cluster-bootstrap CI (nats/token) against the cheapest acceptable arm; secondary = median, p90/p99, top-1 agreement (teacher-forced), first-divergent-position distribution; gate = each arm's mean must exceed the same-engine floor q8f by more than its CI before any ranking is claimed; final choice among arms that are close (silent zone) = task benchmark (TS quality harness), not KLD.

### 5.1 MXFP4 and IQ4
- GGUF, Qwen3.5-35B-A3B (model name inferred, see 1.2): MXFP4_MOE 0.0272 (p99.9 0.779) vs Unsloth Q4_K_M 0.0192, Q4_K_XL 0.0137; IQ4_XS 0.0234-0.0235; noctrex MXFP4_MOE BF16 vs F16 variants 0.0248 / 0.0247. CLAIMED (https://unsloth.ai/docs/models/qwen3.5/gguf-benchmarks). Unsloth text: "MXFP4 is much worse on many tensors", 4.25 vs 4.5 bits/weight for Q4_K, recommends Q4_K.
- MLX, Qwen3.6-27B: MXFP4 0.0479 vs NVFP4 0.0325 vs affine 4-bit 0.0227 vs 8-bit 0.0028. CLAIMED (https://unsloth.ai/docs/models/qwen3.6). So both published views order MXFP4 worse than a K-quant/affine 4-bit of similar size.
- Qwen3-30B-A3B: IQ4_NL 0.0446 vs Q4_K_M 0.0336 (https://huggingface.co/eaddario/Qwen3-30B-A3B-GGUF), IQ4_XS ~ Q4_K_M in Unsloth's table. No source found with IQ4 vs Q4_K on a dense Qwen 27B.
- Accuracy-style (not KLD) comparison, Llama-3.1-8B W4A4: NVFP4 > INT4 (g32) > MXFP4 ("a distant third in terms of accuracy" with RTN/GPTQ, closes the gap with MR-GPTQ). CLAIMED (https://arxiv.org/abs/2509.23202, https://arxiv.org/html/2509.23202, T2). Intel AutoRound claims it beats RTN on MXFP4/NVFP4 (vendor claim; no KLD found).
- NOT usable: a search-snippet claim that MXFP4 beat Q4_K_M by 2x on Qwen3.6-27B (0.0061 vs 0.0123) traced to specpicks.com, which on inspection contains no such numbers and is "editorial synthesis" (https://specpicks.com/reviews/llm-quantization-formats-kld-comparison-2026). Discard.
- Engine/format confound: a KLD comparison of "MXFP4 on vLLM" vs "Q4_K_XL on llama.cpp" mixes quantisation error with the engine path; one author's observation: GGUF in llama.cpp had the lowest KLD at nearly every size (activations unquantised) vs vLLM quants (CLAIMED https://prismix.dev/news/4d0aff670c11). INFERRED: for our MXFP4-on-vLLM arm it is unknown whether activations are also quantised (W4A4 vs W4A16); record it, as it shifts KLD materially.
- Nothing found for Radiance or custom-engine IQ4/MXFP4.

### 5.2 Speculative decoding (DFlash / EAGLE / MTP)
- Theory: rejection-sampling verification leaves the output distribution unchanged ("without changing the distribution", T1-equivalent primary paper, https://arxiv.org/abs/2211.17192; Chen et al. 2023 is the concurrent equivalent, not fetched). vLLM: "theoretically lossless up to the precision limits of hardware numerics", "algorithmically validated" with rejection-sampler convergence tests and greedy-equality tests; hardware numerics "may lead to slight discrepancies in the output distribution"; batch size changes logprobs; model-based methods listed include EAGLE, MTP, draft model, PARD; `dflash` appears as a method value only; "FLy deliberately relaxes verification and is not distribution preserving". CLAIMED (https://docs.vllm.ai/en/stable/features/speculative_decoding/, T1).
- DFlash: verifier-based, block size 16, "6x lossless acceleration"; the paper reports speedup and acceptance length (Qwen3-8B tau ~6.5, non-thinking temp 0) and no quality-with-vs-without table. CLAIMED (https://arxiv.org/html/2602.06036v1, T2).
- Practical drift, all numerics-driven:
  - llama.cpp issue (Apple M4 Pro, Metal, Qwen3.6-27B Q4_K_M, build 9216): `--spec-type draft-mtp` with `--spec-draft-n-max 3` diverged at token 38; n-max 2 / none matched; only maintainer reply noted no fixed seed; closed, root cause unresolved, continued in #23335 (CLAIMED https://github.com/ggml-org/llama.cpp/issues/23302, T1). Low evidential value (unresolved).
  - vLLM fp16, Llama-3.1-8B tool-calling model, 1B draft: 98.8 % exact-match with target-only greedy (1.2 % divergence), 3B draft 99.4 %; attributed to verification batch shapes (single-author blog, T3: https://dev.to/marcuswwchen/speculative-decoding-shifted-our-output-distribution-and-evals-missed-it-4dci).
  - Consumer hardware paper: greedy outputs identical only on a batch-invariant (fp32 CPU) backend; quantised Metal path not (3.4 above).
- INFERRED consequences: (i) spec-on vs spec-off at temp 0 is expected to differ only by the same near-tie numerics that set the q8f floor, not by a systematic distribution shift; (ii) a teacher-forced KLD pass does not exercise speculation at all (no drafting happens when the continuation is supplied), so "spec-on KLD" from a teacher-forced scorer measures the target model's numerics under the spec-enabled server config only; (iii) the meaningful spec test is on greedy trajectories: first-divergent-position distribution and top-1 agreement of spec-on vs spec-off, benchmarked against the spec-off self-run (same two runs without speculation) as the nondeterminism control. If spec-on-vs-spec-off divergence is within spec-off-vs-spec-off, speculation is indistinguishable from the engine's own noise.

## Implications for our method
---------------------------------------------------------------------
1. Rename and re-describe the estimator. It is "a top-20 KL estimator, approximately a lower bound": exact coarse-graining bound only when both sides use the reference-top-20 partition; with the arm's own top-20 tail mass it is not a strict bound (Q2.1). Either (a) keep it and say "approximate, bias roughly -5 to -15 % on the mean, same sign for all arms, ranks preserved in published tests", or (b) add the minimum-KL-subject-to-arm-top-20 solution (the "lower bound" used in the top-200 r/LocalLLaMA benchmark) as a cross-check on one arm to quantify the gap. (b) is a small tool change in kld_probe.py, ask before touching it (iron rule 9).
2. Quote everything as delta over the floor and with paired CIs. Report arm KLD, q8f floor, and paired (arm - q8f) with the cluster-bootstrap CI. Do not rank arms whose paired difference CI includes 0 or whose KLD is within about 1x floor of each other. Subtracting the floor is approximately legitimate because KL is locally quadratic in logit perturbation and independent noise adds (INFERRED); the clamp >= 0 makes noise-only positions one-sided positive, so state that floor rows are slightly inflated by clamping (INFERRED).
3. Make sure the floor matches the path. q8f must be: same engine/build/backend/-b/-ub, reference produced by incremental decode and arm by teacher-forced prefill, `cache_prompt` off. For cross-engine arms (vLLM MXFP4, Radiance) a same-engine q8f understates the floor; add one control per engine family, e.g. a near-lossless checkpoint on that engine (FP8/Q8-class) vs the llama.cpp q8 reference, and cite it as that engine's floor. Same for Vulkan vs ROCm (no published cross-backend KLD exists, Q3.3): either pin one backend for the reference and arms or measure a backend self-pair.
4. Statistics to add to the report: median, p90, p99, share of total KL from the top 1 % of positions, and teacher-forced top-1 agreement, alongside the mean; this reproduces llama-perplexity's "Same top p"/percentile block and exposes tail-dominated means. Keep dNLL, but do not use it to rank.
5. Say explicitly what KLD can and cannot decide. Near-baseline quants (Q8 vs Q6 and probably Q6 vs good Q4) sit in the "silent zone" where KLD/top-1/PPL do not rank task quality (rho ~ 0 in the 2026 preprint). Use KLD to eliminate lossy arms and to quantify engine/numerics drift, and use the TS quality harness for the final close calls.
6. Corpus caveat: absolute KLD is corpus- and tool-dependent (Q8_0 vs BF16 ranges from 1.4e-3 to 7.5e-2 across published setups, Q1.2). Our corpus is code/prose/chat cut mid-text with a GREEDY reference continuation; greedy continuations are lower-entropy than natural text (INFERRED), which probably yields lower KLD than a natural-text or sampled-continuation protocol (Fireworks samples the reference). State this; do not compare our absolute values with llama-perplexity tables. Do not claim our numbers are on the same scale as README/Unsloth tables.
7. Key by token id wherever the engine can return it; assert within-list uniqueness of rendered strings otherwise (the collision bug is the generic cross-engine failure); keep the "reference vs itself must score exactly 0" test as a permanent unit test.
8. Pin and record logprob semantics per arm: vLLM `--logprobs-mode raw_logprobs`, `--max-logprobs >= 20`; llama.cpp `post_sampling_probs=false`, check behaviour at temp 0; Radiance semantics still to be confirmed (the audit note 09 was empty). Record this in each row alongside ROCm/Mesa/build/-b/-ub (iron rule 2).
9. Sample size: 128 prompts x 32 positions has n_eff of roughly 400 if rho ~ 0.3. Expect CIs that are tens of percent of the mean for floor-level arms; prefer more prompts to more positions; report the CI of the paired difference. The ~50-prompt short pass is not to be used for ranking (another author saw rank reversals at that size).
10. Spec decoding rows: treat DFlash/MTP as "lossless in distribution up to numerics". Evidence to collect = spec-on vs spec-off greedy trajectory divergence compared with spec-off self-run divergence (nondeterminism control), not a teacher-forced KLD.
11. MXFP4 expectation: published numbers put MXFP4 worse than Q4_K-class and affine 4-bit at similar size (0.027 vs 0.019 on Qwen3.5-35B-A3B GGUF; 0.048 vs 0.023 on Qwen3.6-27B MLX), so an MXFP4 arm landing above Q4_K_XL is the expected result, not a bug. Record whether activations are quantised.

## What is considered and why (paste-ready paragraph)
---------------------------------------------------------------------
We measure how far each quant or engine moves the model's next-token probabilities from a Q8_0 reference, using KL divergence, the standard "how much information does the quantised model lose per token" metric that llama.cpp's own perplexity tool and most published quant comparisons use. Because several engines can only return their top 20 candidate tokens, we compute the divergence on that top-20 slice plus a lumped remainder, which slightly under- or mis-states the full-vocabulary value but keeps the same sign for every arm; published tests of the same idea find it preserves rankings. To tell real differences from noise we run the reference through the same engine a second time: that self-comparison (about 0.0018 nats per token here) is the floor below which no difference is claimed, and it matches the 1e-5 to 1e-3 floors others report for different batch shapes and kernels. Arms are compared on identical positions with a bootstrap resampled by prompt, since neighbouring tokens in one prompt are correlated and a handful of hard positions dominate the average. We report the mean together with the median, tail percentiles and top-token agreement, because the mean alone hides those few positions. Recent work also shows that for near-lossless quants KLD stops tracking task accuracy, so we use it to rule out lossy configurations and to quantify engine drift, and settle close calls with the task benchmarks. Speculative decoding is lossless in distribution in theory; in practice it differs from plain decoding only through the same floating-point batch effects, so it is judged against the engine's own run-to-run noise.
